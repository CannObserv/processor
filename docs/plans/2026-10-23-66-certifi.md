# certifi ≥ 2026.10.19

## Problem

The services' TLS trust is certifi's bundle, not the system store. `uv.lock` has certifi 2026.07.22, which still holds `emSign ECC Root CA - G3`, the root of the eMudhra-compromised chains (exe.dev advisory). From the live venv, `requests.get` on the advisory's test host returns 200. GCS (`google-auth` / `google-cloud-storage` over `requests`) and the drift check's GitHub calls use it. Nothing overrides certifi (`SSL_CERT_FILE` / `REQUESTS_CA_BUNDLE` / `CURL_CA_BUNDLE`: none in `deploy/`, `src/`, or the unit). 2026.10.19 drops G3 and keeps emSign G1 and C3.

## Approach

- `uv lock --upgrade-package certifi`: the diff moves certifi alone. Never `uv lock --upgrade` (co-core's pin; `tests/test_pin.py`).
- A floor that survives a re-lock: `[tool.uv] constraint-dependencies = ["certifi>=2026.10.19"]`, commented with #66 and the advisory. certifi stays transitive, out of `[project] dependencies`.
- New `tests/test_tls_trust.py` (not `test_pin.py`: that is co-core's pin and its contract):
  - the lock resolves certifi ≥ 2026.10.19, and so does the installed package, compared as dated parts (`2026.7.22` in the lock, `2026.07.22` installed);
  - the installed bundle, parsed as certificates (`ssl` `get_ca_certs()`, not the comment text), has no subject `emSign ECC Root CA - G3`. Positive control: it does have `emSign Root CA - G1`, so the matcher finds the family it looks for.
- DEPLOYMENT.md, a `## TLS trust` note: the trust is certifi's bundle from the release venv; a CA distrust is a certifi bump, a lock change and a deploy; exe.dev's system-store remediation doesn't reach it; the restart is the fix.
