# Processor v1

## Problem

Watcher#325 will issue `content.process` commands and wait for `content.derived` facts. Nothing consumes them yet. This repo holds only the spec. Watcher's cutover (#326) is gated on a shadow window in which Processor's extracted text must hash identically to Watcher's local extraction. Every infra-independent part can be built and tested here now. Credentials, bucket, grants and the broker ACL are pending (broker#75 and the GCP console).

## Approach

The spec is the design of record ([§3](../specs/2026-09-29-processor-service-design.md#section-3--runtime-and-code-structure), [§4](../specs/2026-09-29-processor-service-design.md#section-4--failure-handling), [§7](../specs/2026-09-29-processor-service-design.md#section-7--testing)). The approach is one async process with a serial consumer, a pure extraction core, and thin shells, all built test-first against co-core `==0.19.7`.

The core is `processors/extract.py`, a pure function `(raw, media_type, source_spec) → ExtractOutcome` with no I/O. It runs in a fresh `spawn` child per command. The child sets `RLIMIT_AS` on itself before it imports the extractors, and the parent kills it on timeout.

The per-message logic is `handler.py`, one async function that takes a decoded message plus injected stores, child runner and publisher, and returns a disposition:
- `ack`
- `leave pending`
- `strike`

Every row of the §4 table is one handler test. `consumer.py` is the loop: `ensure_group`, blocking `read(count=1)`, periodic `claim_stale_page`, the in-memory 3-strike counter per entry id, and `dead_letter` for poison frames. It uses co-core-aio's primitives, which have no delivery count or run loop.

Blocking GCS calls run in `asyncio.to_thread`.

Layout:

```
src/processor/
  settings.py
  logging.py
  stores.py
  child.py
  handler.py
  consumer.py
  dlq.py
  __main__.py
  processors/
    __init__.py   # registry
    extract.py
tests/
deploy/processor.service
scripts/
```

Development runs against the local `.wheelhouse`, co-core's `LocalBlobStore`, and the scratch `redis-server`. It never uses the broker or real buckets.

## Tradeoffs / alternatives

- **`ProcessPoolExecutor` (the spec's first wording).** Rejected because it cannot kill a running task on timeout, and a fork of the asyncio + GCS parent makes `RLIMIT_AS` unsizable. The spec was amended in 99ac0e7.
- **One long-lived worker process, respawned only on failure.** Rejected for v1. It saves about 0.5 s of spawn per command, which is noise at ≤ ~100 commands/day, and it adds worker-state and memory-leak concerns. Revisit if an issuer's volume grows.
- **fakeredis for bus tests.** Rejected as the primary target. A real `redis-server` is on this VM and exercises the real `XAUTOCLAIM` and `XGROUP` semantics. Each test gets unique stream names, so tests stay isolated.
- **Retrying a timed-out child immediately in-process.** Rejected. The spec leaves the entry pending and lets the reclaim re-run it. That keeps a slow environmental failure from burning all three strikes in seconds.
- **Click for the DLQ CLI.** Rejected. Three subcommands fit stdlib `argparse`, with no new dependency.

## Steps

1. **Scaffold and pin.**
   - `pyproject.toml` (hatchling src layout; `co-core[extract]`, `co-core-aio[bus]`, `co-core-sync[gcs]` all `==0.19.7`; pydantic-settings; `find-links = ["./.wheelhouse"]`), ruff, pytest, `uv.lock`.
   - `scripts/sync_wheelhouse.py` (Watcher's, reads `gs://co-gcs-pypi`) and `scripts/build_wheelhouse.sh` (from the cannobserv tag).
   - **Red first:** the pin test (the lock's co-core is `0.19.7` and `processor_version(LOCAL_GENERATION) == "0.19.7+1"`).
   - *Done when:* `uv sync && uv run pytest && uv run ruff check .` are green, and editing the pin turns the test red.
2. **Pure core and parity corpus.** `processors/extract.py` and the registry.
   - The corpus is synthetic: HTML, XHTML, a text PDF, a one-page blank PDF (→ `empty`), CSV, XLSX, an unknown essence and `None` (→ HTML), and a spec whose `spec_fingerprint` raises (→ `None`).
   - Goldens are generated by running **Watcher's own** `_extract_and_fingerprint` over the same inputs, at a pinned Watcher commit (`a5d6f34` today).
     - It runs in a scratch Watcher checkout, `uv sync`ed against this wheelhouse, with imports only and no database. `pipeline.py` pulls in SQLAlchemy and Watcher's models, but at import time only.
     - The generator script and the Watcher commit are committed with the fixtures, so parity is cross-implementation, not self-referential.
   - *Done when:* every golden matches, and a no-I/O test (patched `open` / `socket`) passes over the core.
3. **Child runner** (`child.py`).
   - Spawn context, per-command timeout, `RLIMIT_AS` set in the child, and the outcome or exception carried back over a pipe.
   - Four results: `ok`, `raised` (including `MemoryError`), `timeout`, `crashed`.
   - *Done when:* fixture targets that sleep past the timeout, allocate past the limit, and `os._exit(137)` each produce the right result, with no orphaned children.
4. **Stores and settings.** `settings.py` (`CO_PROCESSOR_*`, pydantic-settings).
   - `stores.py` builds the input store (`GcsBlobStore` over `co-gcs-blobs`) and the output store (`GcsBlobStore` over `co-gcs-processor`), or `LocalBlobStore` for dev.
   - Errors are classified: `FileNotFoundError` → `input_unreadable`; GCS 5xx / 429 / timeout / auth → transient.
   - *Done when:* the classifier tests cover each exception family, and `input_uri` must equal `uri_for(input_digest)`.
5. **Handler, which is §4 as code.**
   - Route, validate the digest and URI, read, re-hash, extract in the child, store unless `empty`, then publish `ProcessingCompleteEmit` / `ProcessingFailedEmit`, then ack.
   - Every row of the §4 table gets one test. Further tests cover store → publish → ack order, a publish failure leaving the entry pending, and a 3rd strike publishing `extraction_error`.
   - *Done when:* all rows pass against fakes.
6. **Consumer loop and bus**, tested on the scratch Redis.
   - `ensure_group` at startup, the read loop, the reclaim cadence (min-idle > timeout + store + publish), and `dead_letter` for undecodable frames.
   - `NOPERM` / `OOM` are treated as transient, with backoff on connection loss and a clean SIGTERM drain.
   - Integration: a test issuer `XADD`s real `ContentProcessCommandEmit` wire frames, and the test asserts facts, stored bytes and `XINFO GROUPS` lag.
   - *Done when:* the integration suite is green on `localhost:6379`.
7. **Entry points and ops surface.**
   - `python -m processor run`, `processor dlq list|show|drop`, and JSON logging with the four-key floor.
   - `deploy/processor.service` (`MemoryMax` below VM RAM, `OOMPolicy=continue`, `Restart=on-failure`, `EnvironmentFile=/etc/processor/.env`) and `docs/DEPLOYMENT.md`.
   - *Done when:* a local end-to-end run (scratch Redis, `LocalBlobStore`) processes a command via the CLI, and `systemd-analyze verify` passes on the unit.
8. **Go-live.** Blocked on broker#75, the credential and the GCP grants.
   - **Credential handoff, in broker#75's order.** The operator gives the plaintext `processor` password. `PING` from here as `processor` (`REDISCLI_AUTH` plus `--user`, never a URL on argv). Only then write `/etc/processor/.env`. The broker swaps in the digest line last. Verify before the digest, never after.
   - Right after a good `PING`, create `processor.process` with `ensure_group` (MKSTREAM, from `$`), ahead of the unit's first start. This discharges the hard ordering. broker#75 found `content.process` absent on 2026-09-30, so `$` skips nothing. Watcher was asked on #325 whether early creation suits it.
   - Install the unit and run a smoke read of one real blob to a scratch output prefix.
   - Post `PING` latency for broker's `NETWORK-PATHS.md` as a drafted comment, after approval.
   - *Done when:* `XINFO GROUPS content.process` shows `processor.process` and the broker probe is green.

## Open questions / risks

- **Real-sample parity** (spec §7) needs an export from Watcher: raw digest, spec, resolved `media_type` and recorded fingerprint per item. It was requested on watcher#325 on 2026-09-30. Until it arrives, parity rests on synthetic inputs plus Watcher's own code as the golden generator.
- **Defaults to confirm:**
  - extraction timeout 120 s
  - `RLIMIT_AS` 3 GiB
  - reclaim min-idle 10 min and cadence 60 s
  - unit `MemoryMax` 6 G
  - consumer name `co-processor`

  A poison command reaches its terminal failure after about 30 min (3 × min-idle). At this volume that is acceptable.
- **Duplicate facts (broker#75).** A reclaim re-runs the extraction and publishes a *new* fact with a new `occurred_at`. So a lost `XACK`, or an `XADD` that landed but reported an error, yields two facts with different envelope keys (`command_id:occurred_at`). The spec says Watcher absorbs the duplicate by upserting on `command_id`, but that is unverified on watcher#325.
- **Spec §6's cannobserv doc issue** is already covered by cannobserv#503, filed from the broker side. `CHANGE_BUS.md` and `docs/change_bus/process.md` on cannobserv `main` no longer name Observo.
- **CI** needs WIF as `co-pypi-reader`. The org's WIF attribute condition may not admit this repo yet, so CI is deferred to step 8 unless it does.
- **`LocalBlobStore` vs `GcsBlobStore` parity.** The handler tests use the local store. GCS-specific behaviour (a 412 on an existing object, auth errors) is covered by fakes, not by the real SDK, until the step-8 smoke run.
