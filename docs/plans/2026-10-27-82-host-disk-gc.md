# Adopt the cohort disk GC and headroom sensor

## Problem

co-processor's root disk is 76% full (2026-10-27), and nothing prunes or watches it. Six idle VS Code server builds take most of it. The cohort's answer has shipped: gregoryfoster/skills `maintaining-host-disk`, which installs Provisioner's GC and sensor (VERSION 2) from a pinned co-image-base layer. Processor's pytest also keeps three basetemps (183M).

## Approach

- **Links:** `skills/` and `.claude/skills/` for `maintaining-host-disk`, the same shape as `patching-hosts`. docs/SKILLS.md: 15 → 16. No submodule bump: `a695c02e` contains `6a9daba0`.
- **pytest:** `tmp_path_retention_count = 1` and `tmp_path_retention_policy = "failed"` (repo-knobs.md). `pyproject.toml` is in `RUNTIME_FILES`, so the merge is a deploy.
- **Host config, tracked:** `deploy/disk-gc/disk-gc.conf`, installed by hand as `/etc/cannobserv/disk-gc/disk-gc.conf`, as with `deploy/needrestart.conf.d/`. `scripts/deploy.sh` `HOST_CONFIGS` compares the two, and `tests/test_units.py` accounts for the file. It holds this host's choices:
  - `homes = /home/exedev`;
  - the template's tiers plus `worktrees`, with `worktree_repos = /home/exedev/processor`; no `docker`;
  - `npx_spec_files` set to the deploy checkout's `.claude/settings.json`;
  - lines 85/80;
  - `monitor_id` empty until Status issues one. The PR holds for it, as #42 did.
- **Tests:** `tests/test_disk_gc.py`.
  - Pure parses of the tracked config, under the GC's own parser settings.
  - The host's choices.
  - The pytest knobs.
  - On `co-processor` only, decided by hostname (broker#79): the installed copy matches the tracked one, and the tracked one passes the installed GC's own `load_config`. Both fail, never skip, when the file or the GC is missing.
- **Docs:**
  - DEPLOYMENT.md gets § Disk GC: config, timers, the monitor, the key, its interaction with § Patching, and the run.
  - AGENTS.md's Infrastructure table gets one pointer row.

## Tradeoffs

- **Tracking the config makes every later line change a deploy,** because `deploy/` is runtime. Hand-editing it on the host instead leaves no record and no drift check. Tracking was chosen.
- **The patch window and the GC:** a reboot followed by the GC before VS Code reconnects keeps no build, which costs one ~640M re-download. Accepted and documented, rather than moving `OnCalendar=`.
- **The key is a copy of `/etc/processor/status-checkin.key`,** so a rotation has to update both files.
