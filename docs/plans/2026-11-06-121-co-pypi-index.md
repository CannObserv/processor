# co-core from the co-pypi index (#121)

Brief: #121's body and the coordinator's pre-flight. Template: CannObserv/watcher#358 part 1 (live 2026-11-06T05:33Z). Authorities: cannobserv `docs/RELEASING.md` → *Path C* and `docs/DEPENDABOT.md`. Corrections to the brief are posted on #121 before any build.

## Problem

co-core, co-core-aio and co-core-sync resolve from `./.wheelhouse` through `find-links` (`pyproject.toml:115`). Dependabot's updater can't sync that, so every `uv` security job fails at `PathDependenciesNotReachable: --find-links`, and an advisory reaches us only through the report-only lock audit. `find-links` also locks no hash, which is why #87's digest table, its sync check and its deploy check exist. All three packages are now in an Artifact Registry index Dependabot reads over OIDC (CannObserv/cannobserv#554), and the lock records a sha256 per file from a registry source.

## Approach

Path C, as watcher did, with this repo's rules where they differ:

- **`pyproject.toml`:** an `explicit` `[[tool.uv.index]] co-pypi` at `https://us-west1-python.pkg.dev/co-gcs/co-pypi/simple/` (byte for byte). Each of the three co-core names gets a `[tool.uv.sources]` entry; all three are already direct. `find-links` and `[tool.processor.wheelhouse-sha256]` go. The `wheelhouse` group (`google-cloud-storage`, #79) becomes a `co-pypi` group: `google-auth[requests]`, already in the lock's closure.
- **The relock moves sources and hashes only.** It runs once, from an empty `UV_CACHE_DIR`, through the wrapper. `co-core==0.38.0` stays, so `processor_version` stays `0.38.0+3`. If any other package moves, stop.
- **The proof, one-shot:** the relock commit adds a test that each of the three wheels' lock sha256 equals the table's row. The next commit deletes the table and that test together. History then holds a green commit where both sources agreed. The sdists the index adds have no row: they rest on #554's byte-for-byte read-back, and the report says so.
- **The wrapper:** `bash scripts/co-pypi.sh uv …` → `scripts/co_pypi_token.py`, watcher's shape (refuses anything but `uv`, `exec`s it with `UV_INDEX_CO_PYPI_USERNAME`/`_PASSWORD` in its environment alone, drops `VIRTUAL_ENV`, never prints the token). Two differences:
  - It runs `uv run --project <its checkout> --frozen --only-group co-pypi`, not `--with 'google-auth…'`. watcher's resolves google-auth from PyPI unlocked at run time, inside the process that holds the key. #79's rule is a locked group. `--project` keeps the group in the wrapper's own checkout's venv, while the wrapped `uv` runs in the caller's directory, which for `deploy.sh` is the release.
  - It reads a fixed key path, the deploy host's (decision 1), overridable by `PROCESSOR_CO_PYPI_KEY`. It doesn't read `GOOGLE_APPLICATION_CREDENTIALS`: exedev sets none, and setting one shell-wide would hand every Google client in a dev shell, tests included, an identity.
- **`scripts/deploy.sh`:**
  - The release's `uv sync --locked --no-dev …` runs through the checkout's own `scripts/co-pypi.sh`. *(Revised at build: no `PROCESSOR_DEPLOY_CO_PYPI` seam. The test world's checkout carries a stub at that path, which also proves the checkout's copy is the one used.)*
  - `wheelhouse()`, `locked_wheels()`, `pinned_digests()` and the `.wheelhouse` precondition go.
  - A release whose `uv.lock` still names `registry = ".wheelhouse"` is refused with a pointer (§ Rollback, below).
  - What replaces #87's check: `uv sync --locked` refuses any file whose sha256 misses the lock.
- **CI:**
  - Each WIF step gets `id: auth` and `token_format: access_token`. The two *Sync cannobserv wheelhouse* steps go.
  - The pair goes on each `uv sync` step alone, from the masked output.
  - lint's `uv lock --locked` gets the pair too only if it's measured to need the network (`uv lock --locked --offline` after the relock).
  - `prune-cache` and the "locked to a wheel" check stay, retargeted from `.wheelhouse` to the index: the cache would still hold private co-core.
  - `audit.yml` is unchanged, but its comments move. `uv audit --frozen` is measured with no credential first.
- **`--no-config`** on `shellcheck.sh` and the pre-commit hook existed for `find-links` (`DEPLOYMENT.md:354`). It's re-measured: `uv run --frozen --only-group lint` from an empty cache, with no token. If that's clean, the flag goes; if not, it stays with its new reason.
- **Retired:** `scripts/sync_wheelhouse.py` and `scripts/build_wheelhouse.sh` (#79), `tests/test_sync_wheelhouse.py`, `test_pin.py`'s three wheelhouse tests, and `test_ci.py`'s sync-spelling tests (replaced by the same tests for the wrapper's spelling). Also `.skills/gate-stamp-inputs`' `.wheelhouse/*` line (#115).

A pre-#121 build no longer kept is rebuilt with that commit's own `scripts/deploy.sh`, from a worktree at it with `.wheelhouse` linked. `build_wheelhouse.sh` is still in that commit. ## Tradeoffs / alternatives

- **Keep `find-links` as a fallback:** two sources for one name, which is the shape `explicit = true` exists to prevent. Rejected, as at watcher.
- **Grant `artifactregistry.reader` to `co-gcs-processor-writer`:** widens the runtime identity, which parses untrusted documents, for a deploy-time need. Rejected (pre-flight).
- **`keyrings.google-artifactregistry-auth`:** a new dependency on the deploy path, and it reads ADC, which the host doesn't have. Rejected.
- **Keep deploy.sh able to build pre-#121 locks:** keeps #87's machinery alive for a path the kept releases cover. Rejected for a documented manual path.

## Open questions / risks

**Decision 1: the deploy host's reader key. Decided (operator, 2026-11-06): as recommended.** a new key for `co-pypi-reader@co-gcs` (already `artifactregistry.reader` on `co-pypi`) at `/etc/processor-deploy/co-pypi-reader.json`. The directory is `root:exedev 750`, the file `root:exedev 640`. It goes over SSH stdin as in § GCP provisioning step 5, and the operator creates and places it.
- **Not under `/etc/processor/`,** as the pre-flight has it: that directory is `root:root 700` [measured], so a `640` file inside is unreachable for exedev. Opening it to `710` would loosen the service's own secrets directory for a deploy-time need.
- Only `scripts/co-pypi.sh` reads it, and only as exedev.

**Decision 2: how Dependabot is proven. Decided (operator, 2026-11-06): (b).**
- **(a) Security-only, no `uv` entry.** The proof waits for the next advisory against this lock, which could be weeks away. #121 closes with that line carried on #84.
- **(b) Recommended:** security-only, plus a short-lived `uv` entry in a follow-up PR after the deploy: `allow: [{dependency-name: "co-core"}]`, daily. Then *Check for updates* once and read the log for the OIDC lines and a `200`. Close whatever it proposes unmerged, then remove the entry. It proves the whole chain now, at the cost of two small PRs.
- **(c) The pre-flight's `ignore: "*"`.** dependabot-core drops ignored dependencies before its update checker, so the run likely logs `registered gcp OIDC credentials` and never `authenticating request …` [inferred from dependabot-core's flow, not measured].
- Whichever we pick, admission comes first.

**Risks:**
- **Every `uv lock`, and any `uv sync` that downloads, needs the wrapper.** That includes `uv lock --upgrade-package` of a PyPI package (watcher measured a 401, warm cache or cold).
- **The token reaches what the wrapped `uv` spawns:** build backends, including the project's own hatchling build in each release. It's bounded by the reader role and its hour.
- **The disk GC's `uv` tier can empty the cache,** so every release build mints a token. A missing or bad key fails the build before any switch.
- **The first deploy changes the install source only.** A wheel whose bytes differ would be refused at `uv sync --locked`, not installed.
