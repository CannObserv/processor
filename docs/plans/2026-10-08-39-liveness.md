# Liveness check-in

## Problem

Since the cutover (2026-10-06T21:35:24Z, watcher#326), Processor's output decides production results. If `processor run` stops consuming, nothing tells the operator directly. `co-processor-drift` going `missing` means the drift check is silent, not the consumer. Operator decision (status#24, 2026-10-07): a second monitor, `co-processor-live`, on the same tenant, key and channels.

## Approach

**A heartbeat task inside `processor run`**, beside the consume loop, on the same event loop. It checks in `ok` every `live_interval_s` (300 s) **only while the consume loop is making progress**. When the loop stops making progress, it stays silent, and Status's `missing` is the page. It never sends `alert`.

**Progress (trap 2, design question 1).** `Consumer` records `last_progress` (monotonic):
- when `run` begins,
- after every `step`, whether it succeeded or raised and backed off,
- after every message `_process` handles, including inside a reclaim walk. A walk over a backlog legitimately takes one command's time per entry, so a per-step stamp alone would read a long walk as a wedge.

So the longest legitimate gap is one command plus one blocking read. The heartbeat checks in only while `now - last_progress` ≤ `stale_after`, where `stale_after = reclaim_min_idle_ms + read_block_ms` (605 s by default). That is the bound at which the reclaim already treats a command as dead: it exceeds the extraction timeout plus 60 s by validation, and the GCS-outage worst case (~435 s, per the unit's comment). There is no new knob.
- **Empty queue:** each 5 s read returns empty, and that counts as progress. So "live" means the loop turns, not that work arrived (design question 1).
- **Broker outage:** shows as backoff, which also counts as progress. A broker outage is the broker's own alarm, not Processor being stopped. The variables carry `backing_off` for anyone reading the last check-in.
- **Wedged** (a hung read, an endless walk): silent after 605 s, while the event loop is still up.

**Never in consumption's way (trap 1, design question 3).**
- `post_checkin` is blocking `requests`, so it runs in a **daemon thread**, awaited with `asyncio.timeout(live_checkin_timeout_s)` (10 s).
- It is not run with `asyncio.to_thread`, for two reasons:
  - the default executor is the one the handler's GCS reads and writes use;
  - `asyncio.run` waits for that executor at exit, so a slow-drip Status would hold a stop past `TimeoutStopSec`.
- A check-in still running at the next tick means that tick is skipped and logged, so threads never pile up.
- One attempt per tick, never a retry loop. A failure is one WARNING record and the heartbeat moves on. The 900 s grace absorbs up to three missed ticks.
- Nothing the heartbeat raises reaches the consume loop. Stop cancels it.

**Variables** (every check-in carries all of them; opaque to Status; no templates, since there is never an `alert`): `build`, `last_progress_age_s`, `backing_off` (`"true"`/`"false"`).

**Logging.**
- The first `ok`, and the first `ok` after any failure or silence, log INFO `liveness check-in`.
- A failed check-in logs WARNING with Status's answer.
- A tick skipped as stale logs WARNING, `consume loop stale; not checking in`, with `last_progress_age_s`.
- A steady `ok` logs nothing (288 records a day otherwise).
- The `starting` record gains `liveness`: `on <monitor id>`, `off` (no monitor id: dev, CI), or `off: missing the status-checkin-key credential`.
- A missing key never stops the service. A Status problem must not stop Processor, and the resulting silence pages anyway.

**Settings (trap 4).** A shared base, `StatusSettings`, holds `status_url` and `credentials_directory`, and both classes inherit it:
- `Settings` gains `live_monitor_id` (a ULID, or empty for off), `live_interval_s` (300, > 0) and `live_checkin_timeout_s` (10, > 0, below the interval).
- `DriftSettings` keeps `drift_monitor_id`.

The drift unit still needs no broker settings.

**The unit.** `deploy/processor.service` gains:
- `LoadCredential=status-checkin-key:/etc/processor/status-checkin.key`, plus the `SetCredential=status-checkin-key:\n` fallback, as in the drift unit (#35: an empty `SetCredential=` is rejected by systemd 255);
- `Environment=CO_PROCESSOR_LIVE_MONITOR_ID=<id>`, once Status posts the id.

**The child (trap 3).** The credentials directory now holds `status-checkin-key` next to `gcs-writer-key`. `tests/test_child.py::test_the_child_cannot_read_the_real_secrets` gains `/run/credentials/processor.service/status-checkin-key` and `/etc/processor/status-checkin.key`, so the denial is proven, not assumed.

## The status#24 table (proposed, for approval)

| Field | Value | Why |
|---|---|---|
| `interval_seconds` | 300 | One check-in every 5 min. Commands arrive about hourly, so finer adds noise, not signal |
| `grace_seconds` | 900 | Worst deploy silence: up to 300 s since the last check-in, a 240 s stop (`TimeoutStopSec`, a command finishing), a 300 s verify of a new build that never starts, then a switch back whose old build checks in about 5 s after start. That is about 850 s, under interval + grace = 1200 s. A normal deploy (about 5 s observed) never pages. A wedge pages at most about 605 + 1200 s after it starts |
| `renotify_seconds` | 86400 | Daily, as the drift monitor |
| `title_template` / `body_template` | none | Processor never sends `alert` |
| variables | `build`, `last_progress_age_s`, `backing_off` | Informational |
| created | **disabled** (`enabled: false`) | Its first-check-in deadline is creation + 1200 s, which a merge, CI and deploy can't promise. Status's check-in route takes a check-in on a disabled monitor. Status enables it after the first `ok` lands |

## Decisions for review

1. **Silence, never `alert`.** Status sends a report for every `alert` check-in, with no dedupe, and silence already pages. "Consuming but failing every item" (design question 2) is out of scope: Watcher sees failures per command, and a failure-rate alert would need state.
2. **A stale consume loop is judged on the reclaim's own bound** (605 s), with no new knob.
3. **Backoff counts as alive.** A broker outage doesn't page as "Processor stopped".
4. **The monitor is created disabled.** The id goes into the unit before the merge (as #35's gate 1), and Status enables the monitor after the first `ok`.
5. **The table above.**

## Steps

1. **Tests (red).**
   - `tests/test_liveness.py` (new, no Redis), with the heartbeat driven by a fake progress source and the real `post_checkin` against `http_stub`:
     - fresh progress checks in `ok` with every variable;
     - stale progress stays silent and logs;
     - a Status 5xx or an unreachable Status logs and keeps ticking;
     - a hung Status (stub delay > timeout) is cut off at the timeout, and the next tick is skipped while the thread still runs;
     - stop ends the task promptly, even mid-check-in.
   - `tests/test_consumer.py`:
     - **a hung Status doesn't delay a command**: the stub never answers, the heartbeat runs beside `Consumer.run`, and a command is acked within the time it takes without one;
     - **a wedged consume loop goes silent while the event loop stays up**: `step` hangs, the heartbeat ticks, and no check-in is sent;
     - `last_progress` advances on an empty read, on backoff, and per message in a reclaim walk.

- **The rehearsal (step 6) never stops `processor.service`.** Agreed with Status's agent over a channel, with the outcome on status#29:
  1. Right after a check-in, a PATCH to 60/0.
  2. "has stopped reporting".
  3. A PATCH back to 300/900.
  4. Our next check-in sends "has recovered".
  - It takes about 12 min, from Status's "window open" to "rehearsal done". In that window there is no deploy or restart. If one happens anyway, it is posted to Status at once: the startup tick would recover the monitor early, and the next silence would send a second, false "stopped reporting". Being a PATCH, it needs no watcher#326 heads-up.

- **The first tick is at startup,** right after the canary and the store preflight, so a deploy's first check-in lands within seconds.
