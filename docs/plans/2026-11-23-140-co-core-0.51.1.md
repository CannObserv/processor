# co-core 0.51.1

## Problem

- co-core 0.38.0's `extract` extra caps soupsieve `<3`, so #138 reached 4.1.1 by `override-dependencies`, which replaces co-core's requirement. co-core ≥ 0.46.1 declares `soupsieve>=4.1,<5` itself (cannobserv#667), and `tests/test_lock_floors.py` fails the bump until the override goes.
- co-core 0.51.0 maps `extraction.include_description` (cannobserv#559). Archiver's schema accepts the key (archiver#353) only once Processor runs ≥ 0.51.0. On 0.38.0, a spec that sets the key extracts as if it were absent.
- Since v0.41.0 the blob store reports whether a write created the object (cannobserv#530, `store_reporting`). The epic records that Processor adopts it at this bump.

## Approach

**Target:** v0.51.1, the latest tag on 2026-11-23. Nothing Processor imports changed between 0.51.0 and 0.51.1.

**The bump** (one commit, green on its own):
- `pyproject.toml`: pin all three names `==0.51.1`, and remove `override-dependencies` and its comment.
- Re-lock: `bash scripts/co-pypi.sh uv lock --upgrade-package co-core --upgrade-package co-core-aio --upgrade-package co-core-sync --upgrade-package soupsieve`. Expected: the three move to 0.51.1, soupsieve 4.1.1 → 4.1.3, the `overrides` entry goes, and nothing else moves.
- `tests/test_pin.py`: `EXPECTED` 0.51.1, and `EXTRACTION_STACK` soupsieve 4.1.3. `LOCAL_GENERATION` stays 4 (DEPENDENCIES.md § Extraction dependencies, step 2), so `processor_version` = `0.51.1+4`.
- `tests/test_lock_floors.py`:
  - `OVERRIDDEN` is empty, and one test holds `override-dependencies` to exactly its names, so a stale override fails.
  - soupsieve's 4.1 floor is held by co-core's own requirement (`CO_CORE_FLOORED`), with a test that the requirement floors at 4.1 or higher. If a later co-core drops below that, the test says to add a constraint.
  - The guard's parsing tests stay. The override route is still the documented route for the next capped floor.

**Parity** (DEPENDENCIES.md step 2: the cases come first, so their goldens come from co-core):
- `tests/fixtures/parity/cases.json`:
  - `include_description: true` on `tailscale_security_bulletins.xml` (RSS) and `feed.atom` (Atom), `full_page`;
  - refusals: on `css`, on an HTML body, on `register.xml` (non-feed root), and a non-bool (`"true"`).
- Regenerate: `uv run python scripts/gen_parity_goldens.py tests/fixtures/parity`. Expected: only the new cases appear, and no existing digest moves. The real corpus passes unchanged.

**`store_reporting`** (its own commit, TDD):
- `handler.py` calls `deps.stores.output.store_reporting(...)` and takes `.uri` for the fact.
- `created` goes into the outcome record of a stored, non-empty output, alongside `output_digest`. An empty output stores nothing and logs no `created`.
- It's a log signal only, never a branch. A GCS `False` may be this call's own retried create; a local `True` may be a race.
- `FlakyStore` cases that inject on `store` move to `store_reporting` (correction 5). A test holds that the handler never calls plain `store`.

## Evidence

- **Catch-up:** `git diff v0.38.0 v0.51.1` over every co-core module Processor imports (correction comment).
  - The five contract classes are AST-identical.
  - Extraction differs only by `include_description` (+105/−32 over 8 files).
  - The blob store adds the reporting twins; plain `store` behaves the same.
- **Parity:** the goldens (moved list in the PR), the real corpus unchanged, and `tests/test_child.py` under `required`.
- **soupsieve 4.1.1 → 4.1.3, measured as #138 did:**
  - co-core 0.51.1's `HtmlExtractor`, then `canonical_text_fingerprint`.
  - Inputs: the parity HTML, the real corpus, and host HTML files over 3 KB, each under a selector battery.
  - It runs in two venvs that differ in soupsieve alone. Counts go in the PR.

## Tradeoffs

- **soupsieve rides along:** one more package in the same re-baseline, instead of a later generation bump with its own Watcher notice.
- **`created` is a log signal only:** it's exact in one direction per backend. As a branch it would be wrong on one of them.
