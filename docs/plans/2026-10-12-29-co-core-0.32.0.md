# co-core 0.32.0

## Problem

cannobserv v0.32.0 (tag `v0.32.0`, `33e781a6`) carries cannobserv#523:
- `text/xml`, `application/xml`, `application/rss+xml` and `application/atom+xml` dispatch to a new `XmlExtractor`, where they took the HTML fallback;
- a spec nothing can honour raises `UnsupportedExtractionError(ValueError)`, where it silently meant the whole page;
- `resolve_dispatch_essence` maps `.xml` / `.rss` / `.atom` URLs to the XML essences. That is the contract, so the bump is coordinate-first (D5).

The pin is 0.19.7. Per the operator's catch-up note, whichever of #29 / #37 bumps first takes the full jump.

## The catch-up reading (0.19.7 → 0.32.0)

Checked against the code (`git diff v0.19.7 v0.32.0`), not only the CHANGELOG:
- **Contract models** (`co_core.pure.models.changes`): a docstring only. `extraction_error` now also covers a refused spec; the `Literal` is unchanged.
- **`canonical_text`, `spec_fingerprint`**: unchanged.
- **Bus** (`streams.py`): comments only (`processor.process` documented as live, cannobserv#503/#528). `envelope`, `dead_letter`, `exceptions`, `effects.bus`, `co_core_aio.bus`: unchanged.
- **Blob store** (`util.blobstore`, `util.hashing`, `co_core_sync.drivers.blobstore`): unchanged.
- **Extract**: `xml_feed.py` (new, lxml, already in the extra), `errors.py` (new), the dispatch map, the extension tiebreak, `extraction_config_from_spec`'s refusals, and `refuse_unhonoured` in the HTML, PDF and CSV extractors.
- **Dependencies**: none move. Each package's `pyproject.toml` changes only its version and the sibling floor (`>=0.32,<0.33`).
- **Security fixes in 0.20–0.32**: none recorded.
- Everything else in the range is the WordPress / co/v1 surface, which Processor doesn't import.

So `processors/extract.py` needs no code change: a refusal propagates, the child reports it as `raised`, and the handler publishes `extraction_error`, terminal (spec §4, "Extractor raises").

## Approach

**Pin.** `pyproject.toml` (the three packages), `EXPECTED` in `tests/test_pin.py`, `uv lock`. `LOCAL_GENERATION` stays 1 (ask 2). `scripts/build_wheelhouse.sh`'s default tag follows the pin.

**Refusals are goldens too.** `gen_parity_goldens.py` raises on any case that raises. A case co-core *refuses* is now recorded as `{"refused": "UnsupportedExtractionError"}` (the class name, from co-core's own raise), so the refusal is co-core's output, not Processor's expectation. The catch is `UnsupportedExtractionError` only, imported from `co_core.pure.extract.errors` (inside the import test's allowance): XML and PDF parse failures are plain `ValueError`s, and still name their case and write nothing (a malformed-XML generator test pins that). `moved()` already handles differing field sets, so a spec that starts or stops being refused at a later bump shows in the note.
- `test_extract.py`: a refused golden means `extract()` raises `UnsupportedExtractionError`. The digest test skips refused cases; the no-I/O test runs them too (a refusal does no I/O either).
- `test_child.py`'s whole-corpus run: a refused case comes back `raised`, its detail starting `UnsupportedExtractionError:`, under containment. With the handler's existing `raised` → `extraction_error` row, that is the end-to-end check.
